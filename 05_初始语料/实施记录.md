# 阶段 05：初始语料：实施记录

**状态：执行完成，含已记录的失败（2026-11-01）。**

## 做了什么

- 根据阶段 04 清单，选用 smoke、prescaler、jump、stress-all 四条核心 UVM sequence，每条尝试运行 10 次，共 40 条独立仿真。
- 预注册本地 base seed 505，通过 `random.Random(505)` 和 sequence-major 任务顺序产生各 run seed；使用 4 并发 worker，单次 VCS/URG 宿主 timeout 均为 20 分钟。
- 使用阶段 03 构建的 `simv` 和正确 `dv_root=<OPENTITAN_ROOT>/hw/dv` 环境。每条仿真分别产生 VDB、运行日志、返回码、UVM marker、URG 报告、runtime 数据和哈希清单。
- 所有 40 次 VCS/URG 都返回 0；35 次 UVM PASS。stress-all 的 5 次 UVM 失败均为 `[PH_TIMEOUT] Explicit timeout of 200000000000 ps hit`。没有宿主超时、许可证失败或自动重试。
- 把完整脱敏 manifest、失败列表、总体摘要、执行脚本和 server SHA-256 index 提交到仓库；完整 VDB、URG 报告和日志仍留在服务器。

## 为什么这么做

初始语料需要为每条预先选定的 sequence 提供固定次数、可回放的随机 seed 和原始 coverage 报告。论文没有公开作者的初始语料内容、次数和 seed，因此本阶段记录本项目设置，不宣称其等同论文作者输入。发生失败时保留失败记录，不以补跑替换原始结果。

师兄的 `sequence_based_parallel_test.py` 使用旧 Verisim 配置格式，本阶段没有将其 UART 入口硬套到 VCS。新 runner 保留“每条序列固定运行数、并行执行、逐条 seed 和结果落盘”的用途，并直接调用已验证的 AON Timer VCS 仿真入口。

## 怎么做

- protocol：4 sequences × 10 runs，base seed 505，seed 派生规则和所有 seed 写入 manifest；4 并发，host timeout 20 分钟。
- 仿真参数：`+cdc_instrumentation_enabled=1`、`+ntb_random_seed=<seed>`、`+UVM_TESTNAME=aon_timer_base_test`、对应 `+UVM_TEST_SEQ=<sequence>`、`+en_cov=1`、line/cond/fsm/tgl/branch/assert。
- 单次 UVM 和 URG 流程由 `tools/run_aon_timer_initial_corpus.py` 执行。VCS stderr 合并进每次独立完整日志；无条件不自动重试。
- VCS 返回码为 0 不等于 UVM 通过；以 UVM `TEST PASSED CHECKS`、`UVM_ERROR`、`UVM_FATAL` marker 分类。`PH_TIMEOUT` 的 VDB/URG 作为部分失败诊断保存，排除在成功语料之外。

## 验收与局限

40 次计划尝试、40 个 VDB 和 40 个 URG dashboard 都已生成；UVM 为 35 PASS、5 PH_TIMEOUT。阶段目标的执行记录完整，但不是 40/40 全 PASS。失败来自 stress-all 的 UVM 200 ms 仿真时间上限，需在后续验证是否有合适且预注册的 timeout 策略；本阶段不重跑或修改超时后补替结果。

每个 URG 单次分母显示 4525 group bins，仅作阶段 05 运行记录；阶段 06 需要核验、冻结分析 bin 分母，并显式排除失败运行。初始语料及其 group score 不是论文最终 coverage 或 table-II 对照结果。
