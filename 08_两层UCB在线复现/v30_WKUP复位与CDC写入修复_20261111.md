本轮任务是修复 V22 的 WKUP scoreboard 失败，再从头执行 1000 次 Full。V22 原始源码、可执行文件和结果保留。本轮使用新的服务器源码/build/结果目录，仍使用 V22 的两层 UCB、四个序列 arm、初始 39 条向量、初始覆盖 508/4507、751 个 cluster、seed 42、1000 次提交、10 个 worker 和连续补位。

最终状态：**V30 Full 已于服务器时间 2026-11-11 10:57 完成验收，1000/1000 成功、0 失败、0 重试，覆盖 4127/4507（91.5687%），比初始新增 3619 个 bin。** 5 个已知失败 seed、故障注入、preflight、30 次 smoke、Full 事件/向量/奖励、1000 份原始 UVM 日志、冻结输入/源码哈希及 1039-VDB 独立 URG 合并审计均通过。V22 原件保留；V23/V24 为中止的部分运行，V27/V28 停在回归门禁。

## 重新核查发现的问题

1. **失败 seed 回放误报通过。** 原 V23/V24 shell 脚本没有设置 `dv_root` 和 `SIMULATOR`，VCS 在 TCL 初始化时退出，日志显示 `Time: 0 ps`。进程退出码为 0，旧检查器又只排查非零退出码和 `UVM_ERROR @` / `UVM_FATAL @`，因此把根本没有运行测试的回放误报为通过。此前关于“V23/V24 已通过原失败 seed”的说明撤回；原日志保留为无效回放的诊断证据。
2. **复位后的 timer 检查进程残留。** `check_interrupt()` 的外层 `fork : isolation_fork` 把嵌套 `fork...join_any` 和 `disable fork` 当作两个并行分支。执行 `disable fork` 的分支并不是 timer 子进程的父进程，因此不能清理它们。V24 的高详细度诊断日志中，同一时刻有 3～4 条完全重复的 WKUP count/expired/disabled 记录。V25 在外层增加 `begin/end`，让创建与清理 timer 子进程发生在同一父进程中。单独改这一处仍不能消除 seed `1135891496` 的断言失败，因此它不是全部根因。
3. **WKUP 的等待窗口用错时钟尺度。** 原检查使用预计计时长度加固定传播等待。V23/V24 又分别增加 5/50 个主时钟周期，但本次延迟发生在慢 AON 时钟域。诊断 seed `1135891496` 在断言时实际 WKUP count 已到阈值 7，主中断 pin 和 AON wake pin 仍为 0；下一次 AON 边沿，count=8、AON wake=1；随后主中断 pin=1。主时钟约 10.417 ns、AON 时钟 5 μs，一个 AON 周期约为 480 个主时钟周期，50 个主时钟周期不足以覆盖这段延迟。
4. **计数器高低字与 enable 的 CDC 写入存在竞态。** V27 通过了第一个 seed，但 seed `1202340700` 仍失败。诊断显示，预期写入的 count/threshold 均为 `0xffffffffffffffff`，实际 count 却是 `0xffffffff00000004`，并继续递增，远未达到阈值。软件/TL 写操作返回不代表两个字已在 AON 域全部生效；只等一个 AON 周期就使能，不能保证计数器在完整 64 位值上开始计数。这类失败不能靠延长输出 pin 等待来修复。
5. **保留的 prescaler 相位导致首周期长度变化。** V28 前两个 seed 通过，第三个 seed `709099176` 在连续两个 prescaler 子序列之间失败。V29 仅增加诊断输出，确认失败时配置 prescaler=0、内部 12 位相位=14、实际 count=0、阈值=1。RTL 的 `prescale_count_q` 只在复位时清零，禁用时保持；降低 prescaler 后，相位可能大于新的比较值，必须先环绕才能继续计数。此前增加 4 个 AON 周期仍不足以容纳这种合法状态。
6. **Full 收尾程序存在启动竞态。** 后台进程最初执行 bash launcher，随后才通过 `exec` 切换到 Python runner。只用结果目录是否出现在进程参数中判断存活，会在切换前把正常启动误判为退出。修正为同时识别 Full launcher 和 runner，区分真实退出、僵尸及不相关的 PID；4 项进程生命周期测试通过。此修正只影响等待与收尾，不改变仿真源码、算法或预算。
7. **独立审计脚本入口路径错误。** V30 的首次流程在 30/30 smoke 通过后，因把 URG 审计器路径误指向服务器未部署该文件的仓库 tools 目录而停止。改为使用已经用于 V22、哈希一致的 `scratch/stage08_v22_inputs_20261110/audit_stage08_urg_union_v22.py`，并在启动流程前检查依赖。恢复入口 `--resume-after-smoke` 会重新核验冻结源码、5 个 seed 的真实原日志、故障测试及全部 30 次 smoke；保留现有实验，不重跑或追加这 30 次预算。之后 69-VDB URG 审计通过，Full 才实际启动。

## V30 的修正与检验规则

- 在 V22 独立副本上依次应用 [复位进程作用域补丁](tools/aon_timer_reset_thread_scope_v25.patch)、[AON 等待窗口补丁](tools/aon_timer_wkup_aon_window_v27.patch)、[配置 CDC 同步补丁](tools/aon_timer_wkup_cdc_fence_v28.patch) 和 [分频相位上界补丁](tools/aon_timer_wkup_prescaler_bound_v30.patch)。最后一个补丁替换 V27 的经验性 4 周期窗口，不沿用 V24 的 50 主周期轮询。
- 初始化前先写 WKUP disable，并通过同一 CSR 的 frontdoor 读回确认已停用。配置结束及 jump 写随机 count 后，分别 frontdoor 读回 count/thold 的低、高两字，严格比较实际读值与请求值后才 enable。使用正常 CSR 访问完成 CDC 同步，没有修改 RTL、强制 DUT 内部状态或用读值代替期望值。
- 保留原预测计时与固定传播等待，若 pin 尚未达到期望值，则并行等待中断事件和 `2^12+4=4100` 个 AON 周期的超时。对 12 位计数器，任意合法相位到下一个比较相位的距离不超过 4096 周期；另外 4 周期用于 CDC 余量。中断到来就结束等待，稍等两个主时钟使采样稳定，然后严格比较输出。构建脚本检查冻结 RTL 的 prescale counter 确实为 12 位，避免把此上界用于其他位宽。
- 这验证中断在合法最迟时刻前到达，不声称重建了完整的逐周期黄金模型。正常版本不读取内部 prescaler 相位，也不清零内部相位来绕过合法的跨序列状态。
- 窗口结束后仍执行原来的 `DV_CHECK_CASE_EQ`，没有屏蔽、降级或删除错误，也没有读 DUT 计数器来替代期望值。诊断副本 V26 使用的内部信号读取未加入正常版本。
- 回放脚本显式设置仿真环境，并在各自运行目录中执行 VCS。[新检查器](tools/verify_stage08_uvm_replay.py) 要求进程退出码为 0、`TEST PASSED CHECKS`、完整 UVM summary、`UVM_ERROR/UVM_FATAL=0`、无实际错误报告且仿真时间大于 0。针对零时间退出、缺少 summary、实际错误及非零退出码的 5 项测试已通过。
- [故障注入](tools/check_stage08_wkup_stuck_low_v30.py) 强制 WKUP interrupt/wake 输出为 0。V27/V28/V30 均实测原 WKUP 严格断言触发，`UVM_ERROR=1`、`UVM_FATAL=0`、非零仿真时间；V30 故障测试的仿真时间为 `20941801937 ps`。该故障仿真不进入正常覆盖预算或覆盖并集。
