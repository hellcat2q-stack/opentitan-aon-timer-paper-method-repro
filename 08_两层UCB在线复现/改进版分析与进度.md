# 阶段 08 改进版：分析、方法与进度

## 目的与保护范围

阶段 08 原始目录、算法文件、完整仿真结果均保留为基线。本次改进放在同阶段的独立脚本和服务器新工作目录中，用相同的初始语料、4507-bin 覆盖分母、seed 42、1000 次提交预算、10 个 worker 和逻辑 batch size 10 重新运行，以便做可解释的前后比较。改进版结果不能覆盖或替代原始结果，也不预先声称能达到论文或师兄报告的覆盖率。

## 基线观察

原版 Full 完成 1000/1000 次提交，978 次通过、22 次出现 UVM_ERROR，最终覆盖为 296/4507（6.5676%），较初始并集 233 个 bin 增加 63 个。序列使用量为 jump 274、smoke 267、stress-all 380、prescaler 79。基线证据保存在 `evidence/stage08_full_20261102_v1/`，原始 VCS/URG 数据仍只在学校服务器。

源码复核发现三处会影响调度和 UCB 反馈的行为：

1. `is_sequence_repetition_blocked()` 会阻止当前仍运行中的序列，以及最近刚选择过的序列；后续候选筛选也会排除此类序列。因此即使 jump 持续获得最高 UCB 分数，也可能被改选，和“连续选择高分序列”的策略预期相冲突。
2. `compute_category_gain()` 从 `historical_data`（其中包含 39 条初始向量）统计该序列在 cluster 中命中的 bin 均值。这不是一次在线运行带来的新增覆盖，也不区分目标 cluster 的边际收益，容易让 UCB 以历史静态命中代替在线奖励。
3. 每次提交完成后，原循环都会增加序列运行次数并追加奖励记录，即使该次仿真失败或覆盖解析没有完成。22 次 UVM_ERROR 因此会被当作零奖励观测，改变后续 UCB 的探索项。

## 改进方法

- 移除选择阶段的重复屏蔽。若 UCB 仍把同一序列排第一，允许连续选择；并发 worker 也可运行相同序列，worker 总数仍固定为 10。
- 序列 UCB 奖励按“本次成功且完成解析的运行，在本次目标 cluster 新增的 bin 数”记录。39 条初始向量继续用于发现候选序列，不作为在线奖励样本。每个序列与目标 cluster 分别维护成功观测数和平均增益，使该序列在其他 cluster 的运行不稀释当前 arm 的探索统计。
- 每次仿真完成后立即重评分并补位，使零新增覆盖也能及时进入下一次 UCB 决策；不再等满一个 batch。cluster UCB 和 sequence UCB 的有效观测次数、奖励历史仅由成功且完成覆盖反馈的运行更新。仿真失败仍占用一次预算并留存失败状态，不重试、不提供覆盖奖励；通过的运行即使新增 bin 为 0，也作为有效的零奖励观测记录。
- 对覆盖解析阶段的异常进行失败归档，避免一条成功退出码但缺少有效覆盖反馈的运行混入策略状态。

改进实现位于 `algorithm_source/generic_adaptive_runner_ucb_continuous_refill_norepeat_poolmi_improved.py`，VCS/URG 适配器位于 `tools/run_vcs_ucb_improved.py`，独立启动脚本、smoke gate/full 流程和脱敏导出器分别位于 `tools/launch_stage08_improved.sh`、`tools/complete_stage08_improved.sh`、`tools/export_stage08_improved.py`。原版文件保持不变。针对连续选择、反馈后重评分、目标 cluster 在线奖励、失败反馈和脱敏导出有 6 项独立策略测试 `tests/test_stage08_improved_policy.py`。

## Full 结果与覆盖率分析

1000-submit Full 已完成，独立审计状态为 pass：1000 次提交、978 次成功、22 次失败、0 次重试；最终覆盖 293/4507（6.501%），相对初始并集 233 个 bin 新增 60 个。原版相同预算为 296/4507（6.568%）、新增 63 个、失败同为 22 次。改进版比原版少 3 个 bin，即低 0.0666 个百分点；这次策略改动没有提高最终覆盖，但两版结果基本持平。

改进版序列使用量为 stress-all 366、smoke 259、jump 239、prescaler 136。jump 已能连续选择，最长连续 9 次，说明重复屏蔽修正实际生效；但 jump 的 239 次成功运行没有带来任何全局新增 bin，平均每次仍命中约 56.61 个已覆盖 bin。全部 60 个新增 bin 都由 stress-all 的 13 次成功运行贡献；22 次失败也全部来自 stress-all，均为 UVM_ERROR=1、UVM_FATAL=0。

覆盖仍低的关键原因是内层 UCB 的有效奖励与全局覆盖目标没有对齐。当前 `select_next_sequence()` 实际调用 `compute_category_gain(sequence, target_category)`，而 `record_successful_ucb_feedback()` 为内层 sequence arm 记录的是 `target_category_gain`。1000 次中 978 次成功反馈的目标 cluster 新增奖励只有 3 次大于零；相比之下，全局新增 bin 总数为 60。全局 `new_bins` 虽然写入 `sequence_gain_history`，但对应的 `compute_ucb_scores()` 在当前调度路径中没有调用。因此，UCB 选择层没有依据“哪种 sequence 真正带来全局新覆盖”有效区分 jump、smoke、stress-all 和 prescaler。允许重复和及时补位只能改变调度，不能让本身没有产生新 bin 的 jump 增加新覆盖。

此外，4507 是本项目冻结的 bin 分母，6.501% 不能直接与师兄所说的 70% 比较，除非确认对方使用相同的 coverage 类型、bin 集合、初始语料和 URG 解析口径。70% 若以 4507 为分母，意味着约 3155 个 bin；本次 1000 次只比初始语料多覆盖 60 个。审计还明确注明：映射依赖 Stage06 冻结的 URG 前缀/行序约定，没有独立证明不同报告中的每一行始终对应同一个物理 bin，所以当前百分比和“哪些 bin 新增”的语义仍需做稳定 bin 名称的交叉核验。

下一轮改进前应先完成两项核验：确认师兄 70% 的分母与 URG coverage 类型是否一致；修复内层 sequence UCB 的实际打分，使它使用已验证的全局在线新增奖励（外层 cluster UCB 仍可使用目标 cluster 奖励），并用稳定 bin 标识复核覆盖映射。完成这些工作后再跑同预算 Full，才可以检验是否真正改善覆盖。

## VCS 定向覆盖修正进度（2026-11-05）

### V9 结果与失败原因

30 次 VCS 定向 smoke 全部调用了 `aon_timer_jump_vseq`，但只有 19 次通过、11 次因 `aon_timer_scoreboard.sv:304` 的 WKUP 中断引脚检查失败。30 次 UVM 反馈都确认阈值参数已施加，但目标 coverage bin 命中为 0，最终并集仍为 233/4507（5.1697%）。失败日志显示 scoreboard 已将 WKUP 预期置 1，而实际 WKUP 输出仍为 0。V9 的脱敏摘要、审计、逐次结果、事件链、向量和曲线保存在 `evidence/stage08_vcs_steered_smoke30_v9_20261105/`。

根因假设是 watchdog 定向运行也启用了 WKUP，wake-up 路径会与 watchdog 竞争并提前结束 sequence；另外原 `wait_for_interrupt()` 只等待 AON 域中断/复位引脚，不会等待普通 WDOG bark interrupt。两者都可能导致目标覆盖未采到或 scoreboard/sequence 结束时序不一致。

### V10 修改与验证状态

- 新补丁 `tools/aon_timer_jump_timer_isolation.patch` 对定向运行按目标隔离 WKUP 与 watchdog，仅未定向运行保留同时启用两个计时器的方式。
- watchdog 定向运行改为等待 WDOG bark interrupt 或 bite/reset 信号，并给 scoreboard 留出采样时间。
- 学校服务器上的 VCS 2019.06 V10 build 已成功编译，`simv` 生成完成。
- bark/bite 定向探针在手动停止前没有得到完成结果；因此 V10 尚未通过单例功能验证。不能把编译成功视为仿真修复已验收。
