# 阶段 08 改进版：分析、方法与进度

## 目的与保护范围

阶段 08 原始目录、算法文件、完整仿真结果均保留为基线。本次改进放在同阶段的独立脚本和服务器新工作目录中，用相同的初始语料、4507-bin 覆盖分母、seed 42、1000 次提交预算、10 个 worker 和逻辑 batch size 10 重新运行，以便做可解释的前后比较。改进版结果不能覆盖或替代原始结果，也不预先声称能达到论文或师兄报告的覆盖率。

## 基线观察

原版 Full 完成 1000/1000 次提交，978 次通过、22 次出现 UVM_ERROR，最终覆盖为 296/4507（6.5676%），较初始并集 233 个 bin 增加 63 个。序列使用量为 jump 274、smoke 267、stress-all 380、prescaler 79。基线证据保存在 `evidence/stage08_full_20261102_v1/`，原始 VCS/URG 数据仍只在学校服务器。

源码复核发现三处会影响调度和 UCB 反馈的行为：

1. `is_sequence_repetition_blocked()` 会阻止当前仍运行中的序列，以及最近刚选择过的序列；后续候选筛选也会排除此类序列。因此即使 jump 持续获得最高 UCB 分数，也可能被改选，和“连续选择高分序列”的策略预期相冲突。
2. `compute_category_gain()` 从 `historical_data`（其中包含 39 条初始向量）统计该序列在 cluster 中命中的 bin 均值。这不是一次在线运行带来的新增覆盖，也不区分目标 cluster 的边际收益，容易让 UCB 以历史静态命中代替在线奖励。
3. 每次提交完成后，原循环都会增加序列运行次数并追加奖励记录，即使该次仿真失败或覆盖解析没有完成。22 次 UVM_ERROR 因此会被当作零奖励观测，改变后续 UCB 的探索项。

## 改进方法

- 移除选择阶段的重复屏蔽。若 UCB 仍把同一序列排第一，允许连续选择；并发 worker 也可运行相同序列，worker 总数仍固定为 10。
- 序列 UCB 奖励按“本次成功且完成解析的运行，在本次目标 cluster 新增的 bin 数”记录。39 条初始向量继续用于发现候选序列，不作为在线奖励样本。每个序列与目标 cluster 分别维护成功观测数和平均增益，使该序列在其他 cluster 的运行不稀释当前 arm 的探索统计。
- 每次仿真完成后立即重评分并补位，使零新增覆盖也能及时进入下一次 UCB 决策；不再等满一个 batch。cluster UCB 和 sequence UCB 的有效观测次数、奖励历史仅由成功且完成覆盖反馈的运行更新。仿真失败仍占用一次预算并留存失败状态，不重试、不提供覆盖奖励；通过的运行即使新增 bin 为 0，也作为有效的零奖励观测记录。
- 对覆盖解析阶段的异常进行失败归档，避免一条成功退出码但缺少有效覆盖反馈的运行混入策略状态。

改进实现位于 `algorithm_source/generic_adaptive_runner_ucb_continuous_refill_norepeat_poolmi_improved.py`，VCS/URG 适配器位于 `tools/run_vcs_ucb_improved.py`，独立启动脚本、smoke gate/full 流程和脱敏导出器分别位于 `tools/launch_stage08_improved.sh`、`tools/complete_stage08_improved.sh`、`tools/export_stage08_improved.py`。原版文件保持不变。针对连续选择、反馈后重评分、目标 cluster 在线奖励、失败反馈和脱敏导出有 6 项独立策略测试 `tests/test_stage08_improved_policy.py`。
